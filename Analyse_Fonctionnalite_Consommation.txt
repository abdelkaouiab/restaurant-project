4. ENDPOINTS ET PARAMÈTRES
-------------------------

Consultation JSON :

GET /api/consommations?debut={date}&fin={date}

Téléchargement du PDF :

GET /api/consommations/rapport.pdf?debut={date}&fin={date}

Les paramètres exacts sont :

- debut : date ISO au format yyyy-MM-dd
- fin : date ISO au format yyyy-MM-dd

Les deux paramètres sont convertis en LocalDate.

- Date absente ou non convertible : HTTP 400.
- Date de fin antérieure à la date de début : HTTP 409.
- Période supérieure à 366 jours calendaires inclusifs : HTTP 409.


5. RÈGLE DE SÉLECTION DES COMMANDES
----------------------------------

Les commandes sont sélectionnées selon leur champ confirmee_le et les statuts suivants :

- CONFIRMEE
- EN_PREPARATION
- PRETE
- PAYEE

Les statuts BROUILLON et ANNULEE sont exclus.

Le filtre SQL appliqué est équivalent à :

confirmee_le >= début de la période
confirmee_le < lendemain de la date de fin
statut IN ('CONFIRMEE', 'EN_PREPARATION', 'PRETE', 'PAYEE')


6. CALCUL DES PRODUITS CONSOMMÉS
-------------------------------

La requête additionne les quantités des lignes de commande :

sum(l.quantite)
group by p.id, p.nom

La quantité totale d’un produit correspond à la somme de ses quantités dans toutes les
lignes des commandes retenues. Un produit présent dans plusieurs commandes apparaît donc
une seule fois avec une quantité cumulée.


7. CALCUL DES INGRÉDIENTS UTILISÉS
---------------------------------

La requête utilise les recettes enregistrées dans produit_ingredients et calcule :

sum(pi.quantite * l.quantite)
group by i.id, i.nom, i.unite

Pour chaque produit commandé, la quantité de chaque ingrédient prévue dans la recette est
multipliée par la quantité commandée du produit. Un ingrédient partagé entre plusieurs
produits est regroupé grâce au GROUP BY sur son identifiant, son nom et son unité.

Point factuel important : le rapport utilise la recette actuellement enregistrée dans
produit_ingredients. Il n’utilise pas un instantané historique de la recette au moment où
la commande a été confirmée.


8. GESTION DES UNITÉS
---------------------

Les unités backend sont celles de l’énumération UniteMesure :

- GRAMME
- KILOGRAMME
- MILLILITRE
- LITRE
- UNITE

Les quantités d’ingrédients sont retournées en BigDecimal avec une échelle de trois
décimales. Les quantités de produits sont entières et représentées par un long.

Le frontend traduit les unités en :

- GRAMME -> g
- KILOGRAMME -> kg
- MILLILITRE -> ml
- LITRE -> L
- UNITE -> unité

L’écran affiche au maximum trois décimales. Le PDF affiche les quantités d’ingrédients avec
trois décimales.

La migration V13 existante impose des quantités entières aux ingrédients dont l’unité est
UNITE. Cette migration précède la fonctionnalité Consommation et ne lui appartient pas.


9. INTERPRÉTATION DES DATES
---------------------------

PeriodeConsommation transforme la période en UTC :

- début : date debut à 00:00:00 UTC, incluse ;
- fin exclusive : lendemain de la date fin à 00:00:00 UTC.

La condition SQL est donc :

confirmee_le >= debutInstant
confirmee_le < finExclusive

Toute la journée correspondant à la date de fin est incluse.


10. SOURCE UNIQUE DE CALCUL
---------------------------

ConsommationService constitue la source unique de calcul :

- l’endpoint JSON appelle ConsommationService.consulter(...) ;
- ConsommationPdfService appelle également ConsommationService.consulter(...).

L’écran et le PDF obtiennent donc leurs données à partir du même service métier et des
mêmes requêtes.


11. GÉNÉRATION DU PDF
---------------------

Le service exact est ConsommationPdfService.

La bibliothèque utilisée est Apache PDFBox 3.0.8. Elle existait déjà dans le projet pour
FacturePdfService et les tests de paiement. Aucune nouvelle dépendance PDF n’a été ajoutée
par la fonctionnalité Consommation.

Le nom du fichier généré est :

rapport-consommation-{debut}-au-{fin}.pdf

Exemple :

rapport-consommation-2026-08-01-au-2026-08-31.pdf

La réponse possède :

- Content-Type: application/pdf
- Content-Disposition: attachment


12. SÉCURITÉ BACKEND
--------------------

Les endpoints sont couverts par la règle générale Spring Security :

.anyRequest().authenticated()

Les contrôles de rôles sont appliqués aux services avec l’annotation exacte :

@PreAuthorize("hasAnyRole('ADMINISTRATEUR','GERANT')")

Cette annotation se trouve sur :

- ConsommationService.consulter(...)
- ConsommationPdfService.generer(...)

Il n’existe pas d’annotation @PreAuthorize directement sur ConsommationController.

Les tests confirment les comportements suivants :

- utilisateur non authentifié : HTTP 401 ;
- rôle SERVEUR : HTTP 403 ;
- rôle ADMINISTRATEUR : HTTP 200 ;
- rôle GERANT : HTTP 200.


13. ROUTE ET SÉCURITÉ FRONTEND
------------------------------

La route React exacte est :

/consommation

Sa configuration contient :

rolesAutorises: ['ADMINISTRATEUR', 'GERANT']
permissionsRequises: []

Cette configuration masque le lien du menu pour les autres rôles. Un accès direct avec un
rôle non autorisé rend ForbiddenPage. La protection frontend améliore l’interface, tandis
que le contrôle de sécurité faisant autorité reste celui du backend.


14. COMPOSANTS ET API FRONTEND
------------------------------

ConsommationPage :

- initialise par défaut les trente derniers jours, aujourd’hui inclus ;
- réutilise PeriodeForm et validerPeriode ;
- charge les produits et ingrédients ;
- présente deux tableaux ;
- gère le chargement, les erreurs, le cas vide et le téléchargement PDF.

consommationApi :

- consulter(...) utilise apiRequest pour l’endpoint JSON ;
- telechargerPdf(...) utilise apiBlob pour l’endpoint PDF ;
- les cookies de session sont inclus par le client API commun.

Téléchargement du PDF :

1. Le Blob est reçu par apiBlob.
2. Une URL locale est créée avec URL.createObjectURL.
3. Un élément HTML <a download> est construit et cliqué.
4. L’URL locale est libérée avec URL.revokeObjectURL.


15. COMPORTEMENT SANS DONNÉES
-----------------------------

Lorsque la période ne contient aucune consommation :

- le backend retourne HTTP 200 ;
- produits vaut [] ;
- ingredients vaut [] ;
- l’écran affiche « Aucune consommation enregistrée pour cette période. » ;
- le bouton de téléchargement PDF reste disponible ;
- le PDF est produit et contient le même message d’absence de données.

INFORMATIONS RECOMMANDÉES POUR LE RAPPORT DE STAGE
==================================================

1. La fonctionnalité Consommation fournit une synthèse des ventes et des ingrédients utilisés sur une période.
2. Elle expose un endpoint JSON et un endpoint de génération PDF.
3. Les dates sont transmises au format ISO avec les paramètres debut et fin.
4. La période est interprétée en UTC et inclut entièrement la journée de fin.
5. Seules les commandes CONFIRMEE, EN_PREPARATION, PRETE et PAYEE sont comptabilisées.
6. Les brouillons et les commandes annulées sont exclus.
7. Les produits sont regroupés et additionnés à partir des lignes de commande.
8. Les ingrédients sont calculés en multipliant les quantités des recettes par les quantités commandées.
9. Un ingrédient partagé entre plusieurs produits est agrégé dans une seule ligne.
10. Les unités gérées sont le gramme, kilogramme, millilitre, litre et unité.
11. ConsommationService centralise le calcul utilisé par l’interface et par le PDF.
12. Le PDF est produit avec Apache PDFBox et reprend les mêmes données que l’écran.
13. L’accès est réservé aux rôles ADMINISTRATEUR et GERANT.
14. Le frontend masque la route aux autres rôles, tandis que le backend garantit le contrôle d’accès.
15. La fonctionnalité gère explicitement les périodes sans consommation.
16. Elle n’a nécessité ni nouvelle table, ni migration Flyway, ni nouvelle dépendance.
17. Les vérifications donnent 114 tests backend et 104 tests frontend réussis.
